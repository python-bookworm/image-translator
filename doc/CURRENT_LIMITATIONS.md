# 当前不足与改进建议

## 1. 说明

本文是对当前仓库的静态代码审阅结果。本次仅记录问题，不修改业务代码。优先级定义如下：

- **P0**：安全事件或核心路径确定性故障，应立即处理。
- **P1**：高概率影响主要场景、数据安全或稳定性，应优先进入下一迭代。
- **P2**：影响质量、可维护性或部分边界场景，可排入常规迭代。
- **P3**：体验和工程完整性改进。

## 2. 已确认问题

### P0：示例环境文件包含非空大模型凭据

位置：`.env.native.example`

示例文件中的 `LLM_API_KEY` 当前不是空值。示例配置通常会被复制、打包、提交或发送给其他人员，因此无论该值是否仍然有效，都应视为已经泄露。

影响：未授权调用、额度或资源消耗、内部服务访问风险、审计责任不清。

建议：立即在大模型网关吊销并轮换该凭据；将所有 `.env.*.example` 的密钥恢复为空；检查 Git 历史、压缩包、服务器副本和聊天传输记录。仅从服务器私有配置或密钥管理系统注入真实凭据。

### P1：截图兜底分支引用未定义变量

位置：`extension/service-worker.js` 的 `translatePreviewTab()`。

函数最后调用 `savePreviewResult(..., sourceUrl)`，但该函数作用域内没有 `sourceUrl`。当非 HTTP(S) 图片或受限预览进入截图兜底并完成后端翻译后，会触发 `ReferenceError`，导致结果页不能打开。

建议：使用 `tab.url` 或显式增加函数参数，并为该分支增加自动化测试。

### P1：敏感业务文本以 INFO 级别完整写入日志

位置：`app/pipeline.py`、`app/services/translator.py`。

日志包含图片路径、OCR 原文、大模型输入和翻译结果。当前截断上限仍可达到数千字符，OA、财务、合同或个人信息图片可能把敏感数据长期保存在日志中。

建议：生产默认只记录请求 ID、区域数、耗时和错误类别；正文日志改为显式调试开关并默认关闭；增加日志轮转、权限、脱敏和保留周期。

### P1：后端没有认证、授权和调用方限制

位置：`app/main.py`。

任何能够访问端口的客户端都可以调用 OCR、GPU 和大模型资源。CORS 只限制浏览器页面读取响应，不构成服务端访问控制。

影响：内部滥用、GPU 资源耗尽、恶意大图请求、LLM 成本和敏感图片外发。

建议：通过内网 HTTPS 反向代理增加身份认证、访问控制、请求速率限制和最大请求体；必要时在 API 层增加短期令牌或公司统一身份认证。

### P1：插件权限范围过大

位置：`extension/manifest.json`。

插件使用 `<all_urls>` host permission 和 Content Script 匹配，同时声明 `tabs`、`activeTab`、`scripting`。对内部 POC 虽然方便，但权限告警明显，任一插件代码供应链问题的影响范围也更大。

建议：按公司实际 OA 域名和图片来源收敛 host permissions；评估是否确实需要 `tabs` 和 `scripting`；对可选站点使用 `optional_host_permissions` 和用户授权。

## 3. 架构与稳定性不足

### P1：网络 LLM 调用占用全局推理锁

位置：`app/pipeline.py`。

OCR 和翻译整体位于同一个 `_inference_lock` 中。大模型调用最长可等待数分钟，在此期间其他请求连 OCR 都无法开始。单个慢请求会阻塞整个进程。

建议：分别管理 OCR/GPU 模型锁和翻译并发；外部 LLM 网络调用移出 OCR 锁；增加有界队列、并发上限、排队超时和繁忙响应。

### P1：同步长任务缺少任务状态和取消机制

接口在一个 HTTP 请求中完成下载、OCR、LLM 翻译、渲染和返回。浏览器、代理或用户提前关闭页面后，服务端仍可能继续消耗 GPU 和 LLM 资源。

建议：小规模阶段至少增加请求超时分层和断开检测；规模扩大后考虑任务 ID、状态查询、取消和结果短期存储。

### P1：LLM OCR 文本存在提示注入风险

OCR 内容直接进入用户消息。恶意图片可以包含“忽略要求并输出其他内容”等指令。当前虽然严格校验 JSON 和 ID，但无法保证译文语义未被操纵，也未使用模型服务的 JSON schema/response format。

建议：优先使用支持结构化输出的接口；把 OCR 数据置于明确的数据边界中；限制输出长度；增加翻译质量和异常内容检测；对高敏感场景使用受控本地模型。

### P2：LLM 自动识别按批次进行且只采用第一个结果

一张图片 OCR 区域超过 `LLM_BATCH_SIZE` 时，每批独立检测语言。代码在检测结果不一致时仅记录警告，最终返回第一批语言。混合语言图片或第一批文本很短时容易误判。

建议：先对全图代表性文本执行一次语言检测，再按统一语言翻译；或保留区域级语言并支持多语言翻译。

### P2：纯 LLM 部署仍被 NLLB 模型校验绑定

`validate_models.py` 总是要求完整 NLLB 文件，后台和容器启动脚本也总是调用该校验。即使配置为 LLM 且关闭 NLLB 回退，仍无法进行不带 NLLB 的轻量部署。

建议：让模型校验读取当前配置，按翻译提供者和回退选项决定是否检查 NLLB、Torch 和 fastText。

### P2：Docker 配置没有透传 LLM 代理选项

原生配置支持 `LLM_USE_ENV_PROXY` 和 `LLM_PROXY`，但 `compose.yaml` 没有把这两个变量传入容器。需要代理的 Docker 部署无法只修改 `.env.linux` 生效。

建议：在 Compose environment 中显式透传两个配置，并为直连、继承代理和显式代理三种模式增加配置校验。

### P2：健康检查只能证明进程存活

`/health` 不验证 OCR 模型可推理、GPU 是否仍可用、大模型端点是否可达、字体是否存在。服务启动后发生 GPU 故障或 LLM 断路时仍返回 `ok`。

建议：区分轻量 liveness 和可选 readiness；readiness 返回各依赖状态但避免每次执行昂贵推理。

## 4. 插件不足

### P1：跨域 iframe、Shadow DOM、Canvas 和 CSS 背景图支持有限

Content Script 默认只运行在顶层文档，目标定位只扫描 `document.images`。OA 预览组件若在 iframe、封闭 Shadow DOM、Canvas 或 `background-image` 中，无法原位替换，只能依赖结果页兜底。

建议：先采集真实 OA 页面结构，再按域名做受控适配；支持 frameId 消息路由和同源 iframe；对 Canvas/背景图采用截图而不是假定存在 `<img>`。

### P1：受保护图片的登录上下文不稳定

Service Worker 使用 `fetch(sourceUrl, {credentials: "include"})`，但扩展请求不保证携带页面所需的 Referer、SameSite Cookie、分区 Cookie或临时请求头。用户能在页面看到图片不代表扩展能再次下载。

建议：对实际 OA 域名验证 Cookie/Referer 行为；必要时由 Content Script 从可访问元素读取、使用页面截图，或由受控后端根据授权 URL 获取；不要尝试绕过浏览器安全策略。

### P2：失败后可能重复执行完整翻译

普通流程在开始消息未定位到图片时，会转入直接预览路径并重新获取、提交图片。当前发生在后端调用前，问题不大；但今后扩展错误分类若扩大，需避免已经成功后再次调用后端。

建议：明确区分“开始前注入失败”“后端处理失败”“结果回写失败”，并让成功结果始终复用同一 Blob 和请求 ID。

### P2：语言列表在前后端重复维护

`app/languages.py` 和 `extension/popup.js` 各自维护语言清单，后端虽提供 `/v1/languages`，插件没有使用。新增语言或修改名称时可能出现不一致。

建议：插件连接成功后从后端加载语言列表，并保留内置最小列表作为离线兜底。

### P2：IndexedDB 清理依赖下一次保存

一小时过期结果只在 `cleanupResults()` 被新保存操作调用时删除。长期不再使用插件时，旧 Blob 会继续占用浏览器存储；结果页读取后也不删除记录。

建议：结果读取后按策略删除，或使用扩展 alarm 定期清理，并设置记录数量和总字节上限。

### P2：Data URL 带来明显内存放大

普通网页译图先从 Blob 转成 Base64 Data URL，再通过消息传给 Content Script。Base64 约增加三分之一体积，字符串复制还会造成额外峰值内存。25 MB 阈值下实际占用可能远大于 25 MB。

建议：降低内联阈值；大图直接使用结果页；评估扩展资源 URL、Blob 传输或分块方案。

### P3：结果页中英文不一致

Popup 和网页工具条主要使用中文，结果页标题、按钮、错误和元数据显示英文及语言代码，内部用户体验不统一。

建议：统一中文界面，并将语言代码映射为中文名称。

### P3：图标只引用一张非标准尺寸原图

`manifest.json` 的 16、32、48、128 尺寸均引用同一张 `622 x 599` 图片。Chromium 可以缩放，但小尺寸清晰度和方形裁切效果不可控。

建议：保持 `3.png` 为视觉源图，生成方形留白后的 16、32、48、128 PNG 派生资源。

## 5. OCR、翻译与渲染质量不足

### P1：OCR 多语言覆盖依赖单一识别模型

语言列表覆盖阿拉伯语、泰语、高棉语、印地语等多种文字体系，但当前只加载一个 `PP-OCRv5_server_rec`。翻译模型支持某语言并不代表 OCR 能识别其文字。

建议：用实际业务图片按语种建立 OCR 基准；对不覆盖的文字体系增加语言到识别模型的路由，或使用明确支持相应脚本的多语言 OCR 模型。

### P2：逐 OCR 行翻译缺少上下文

每个检测区域作为独立字符串交给翻译器。标题、表格、跨行句子和段落会丢失上下文，术语和指代容易不一致。

建议：按空间关系将文字区域组合为段落或表格单元，翻译后再映射回原区域；同时保留 ID 以确保布局对应。

### P2：渲染只使用轴对齐矩形

原文字按多边形清除，但译文绘制到多边形的轴对齐包围盒。旋转文字、透视文字、竖排文字和弯曲文字不会沿原方向排版。

建议：根据多边形角度旋转临时画布后合成；为竖排和 RTL 语言增加方向处理。

### P2：最小字号下仍可能溢出或被截断

当译文在最小字号下仍无法放入区域时，`_fit_text()` 直接返回最小字号换行结果，没有缩略、扩展区域、覆盖检测或溢出标记。

建议：增加溢出判断；可按业务选择扩大背景框、缩短译文、绘制引线标注或在结果页提供文字列表。

### P2：阅读顺序算法过于简单

区域只按最小 Y、最小 X 排序，没有行聚类、栏位识别、表格结构和 RTL 阅读顺序。多栏文档、票据和复杂版式可能以错误顺序送入翻译。

建议：引入行聚类和版面分析；对表格、票据、段落采用不同分组策略。

## 6. 测试与工程不足

### P1：没有浏览器扩展自动化测试

当前测试只覆盖少量 Python 辅助函数，没有验证右键菜单、消息 ACK、原位替换、结果页兜底、截图分支、Chrome/Edge 差异和 iframe 场景。这也是截图分支未定义变量未被发现的直接原因之一。

建议：使用 Playwright 加载解压扩展，准备普通图片页、动态图片页和 iframe 页；对 Service Worker 日志、后端请求次数、原位结果和结果页进行断言。Chrome 与 Edge 至少各保留一轮人工验收。

### P1：缺少 API 和完整流水线集成测试

没有使用 FastAPI TestClient 验证参数、响应头、400/500、大小限制和 CORS；也没有使用假的 OCR/翻译器测试区域数量与渲染编排。

建议：通过依赖注入或可替换工厂隔离重模型，建立快速、确定性的 API 测试和流水线契约测试。

### P2：测试覆盖面较窄

当前单元测试覆盖语言映射、OCR payload 提取、图片解码、字符换行和 LLM JSON 解析，但没有覆盖 LLM 超时与回退、自动检测、代理配置、渲染溢出、模型校验模式和启动脚本。

建议：优先覆盖错误分支和配置组合；在 Linux GPU 环境增加独立的模型冒烟测试，不与快速单元测试混在一起。

### P2：版本和文档存在漂移

FastAPI 应用版本为 `0.1.0`，插件为 `0.2.1`，Compose 镜像标签为 `0.1.0`。README 中部分流程仍以 NLLB 为主，而当前推荐配置是 LLM。

建议：定义统一发布版本和变更记录；发布时同步更新后端、插件、镜像标签和文档。

### P2：仓库中保留了旧图标和打包产物

`extension/icons` 同时包含旧竹牛 SVG/PNG 与当前 `3.png`，根目录还有 `extension.zip`。若压缩包未随源码更新，用户可能安装旧插件；无引用资源也增加分发混淆。

建议：明确构建产物生成流程和版本；发布包由脚本生成并校验 manifest；确认无引用资源后再清理，避免手工压缩包漂移。

## 7. 建议整改顺序

1. **立即处理安全事项**：吊销示例文件中的凭据，检查传播范围；限制后端暴露范围；制定敏感日志策略。
2. **修复确定性故障**：截图兜底未定义变量，并为三条插件路径增加测试。
3. **完善服务保护**：认证、HTTPS、限流、请求大小、队列和超时。
4. **改善并发结构**：外部 LLM 调用移出 OCR 全局锁，增加有界并发与繁忙状态。
5. **验证业务覆盖**：按目标语种建立 OCR 与翻译基准，重点验证 OA、财务票据和小语种。
6. **扩展自动化测试**：API、流水线、Chrome/Edge 扩展和部署配置。
7. **提升结果质量**：段落分组、版面分析、旋转/竖排/RTL、溢出处理和字体策略。

在当前内部小批量 POC 阶段，最小可接受闭环是：凭据和日志风险得到控制，截图分支修复，普通网页/直接图片/OA 附件三类路径都有可重复的验收用例，并对后端入口增加基础访问控制。
